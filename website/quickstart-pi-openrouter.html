WorksGood · Quickstart

WG + Pi + a free OpenRouter model, in 9 steps

The canonical copy-paste path from a clean machine to a live wg tui driving a free OpenRouter model through Pi, at zero cost — so you can confirm the whole wiring before spending credits. The same path lives in the repo; if anything disagrees, the markdown file is the source of truth.

Verified against wg 0.1.0 and @earendil-works/pi-coding-agent 0.82.0. Re-check commands against your installed versions — see Troubleshooting when something differs.

0The five names

IdentityWhat it is
WorksGoodthe product / project
worksgoodthe installed attended lifecycle concierge (setup, status, stop, restart, tui)
wgthe installed complete expert task/tool CLI; Pi tools invoke this backend
@worksgood/pinpm name of the WorksGood↔Pi integration. Not installed from npm today — the version-locked build is embedded in the wg binary and installed by wg pi-plugin install.
pi-worksgoodthe label Pi shows for the integration (tools, /wg commands).

Pi (@earendil-works/pi-coding-agent) is a separate product. WorksGood uses Pi as its sole LLM model plane: Pi owns provider login, model discovery, endpoints, availability, and cost; WorksGood owns the task graph plus exact per-role pi:<provider>:<model> routes.

Heads-up on the wg name. It collides with WireGuard's wg(8). If you also use WireGuard, install WorksGood's expert wg on a private path. The human-facing worksgood command ships by default. There is deliberately no worksg alias, and Pi integrations still call the full wg backend.

1Install WorksGood (worksgood + wg + nex)

Requires the Rust toolchain (rustup).

cargo install --git https://github.com/graphwork/wg --locked
worksgood --help
wg --version
nex --version

From a source checkout: cargo install --path . --locked. Make ~/.cargo/bin reachable:

# bash/zsh — add once, then: source ~/.bashrc
echo 'export PATH="$HOME/.cargo/bin:$PATH"' >> ~/.bashrc

2Install Pi

Pi is an npm package. Requires Node.js 20+.

npm install -g --ignore-scripts @earendil-works/pi-coding-agent
pi --version

macOS — install Node first (brew install node, or nvm), then the same line.

Termux (Android) — see Pi's Termux guide:

pkg update && pkg upgrade
pkg install nodejs git
npm install -g --ignore-scripts @earendil-works/pi-coding-agent

3Authenticate Pi with OpenRouter

Do this once, in Pi — WorksGood never sees or stores your key.

cd /path/to/any/project
pi                              # start an interactive Pi session

Inside Pi:

/login openrouter

then choose Sign in with OpenRouter. This opens OpenRouter's PKCE OAuth flow in your browser; Pi stores a user-controlled API key (minted from your OpenRouter credits) in ~/.pi/agent/auth.json with 0600 permissions. Sign out any time with /logout.

Safe key handling — never put a secret in shell history. Prefer /login. If you can't use OAuth, store the key in Pi's auth.json (via /login → “Use an API key”) or export it from your shell rc — never type pi --api-key sk-or-..., which lands in history and the process list. Resolution order in Pi: --api-key flag → ~/.pi/agent/auth.json → env var → models.json. See Pi's Providers.

You may need a small amount of OpenRouter credit even for :free models; free models also have per-day/per-minute caps. Check your allowance at openrouter.ai/keys.

4Find a currently-available free model

Free OpenRouter models carry a :free suffix. Availability, context, rate limits, and tool support change frequently — discover them at run time, never hard-code one.

pi --list-models ":free"

A credential-free listing of every currently-free OpenRouter model Pi knows:

provider    model                                               context  max-out  thinking  images
openrouter  google/gemma-4-31b-it:free                          262.1K   32.8K    yes       yes
openrouter  nvidia/nemotron-3-ultra-550b-a55b:free              1M       65.5K    yes       no
openrouter  openai/gpt-oss-20b:free                             131.1K   32.8K    yes       no
...                                                  (the list rotates over time)
nvidia/nemotron-3-ultra-550b-a55b:free is a dated snapshot, not an eternal default. Re-run pi --list-models ":free" and read the model card at openrouter.ai/models for current limits, context size, vision, and tool/function-call support (some free models lack tool support, which affects agent dispatch).

Validate the model actually works in Pi (needs the auth from step 3):

pi --model "openrouter/nvidia/nemotron-3-ultra-550b-a55b:free" -p "Reply with the single word OK"

A 401 means re-do /login; a 404 means the id is wrong/withdrawn — re-list and pick another. This is the exact point that requires interactive OpenRouter login; everything before it is credential-free.

5Install the WorksGood Pi integration (pi-worksgood)

One command materializes the version-locked build embedded in your wg binary and wires it into Pi's global settings:

wg pi-plugin install

Expected:

Installed pi-worksgood (npm: @worksgood/pi, compat 0.2.0) from embedded → versioned cache.
  extension: ~/.cache/wg/worksgood-pi/0.2.0/pi-worksgood/index.js
  wired into pi settings: ~/.pi/agent/settings.json

Verify:

wg pi-plugin status          # source, cache path, compat, console wired: yes
wg pi-plugin path            # scriptable resolved index.js path
wg pi-plugin compat-version  # the compat version the plugin asserts

A human-run pi now auto-loads the pi-worksgood tools (wg_ready, wg_show, wg_add, wg_done, …) and /wg commands.

Idempotent + self-healing. Re-run wg pi-plugin install any time; it no-ops when correct and repairs drift. Hermetic for WG-spawned workers: WorksGood loads exactly the embedded build by absolute path (pi --mode rpc -e <cache>/pi-worksgood/index.js -ne) and never reads ~/.pi on that path. Only the human-console direction uses the global settings entry written here.

Legacy migration. If you had the old @worksgood/wg-pi-plugin, wg pi-plugin install keeps it inert, points Pi at the one compatible pi-worksgood/index.js, and prints a one-time pi remove npm:@worksgood/wg-pi-plugin command.

6(Optional) Give Pi web capabilities

Two separate official Pi packages — they are not the same thing:

PackageWhat it adds
pi-web-accessweb search, URL/page fetching, GitHub repo cloning, PDF extraction, YouTube & local video understanding
pi-agent-browser-nativeinteractive browser automation (open, click, fill, screenshot, drive real web apps)
 
pi install npm:pi-web-access               # search + fetch + clone + video
pi install npm:pi-agent-browser-native     # real browser driving
pi list                                    # confirm what's installed

Search/content access is read-only research; browser automation actively drives a real browser (log in, click, submit). Independent of the WorksGood integration. Remove with pi remove npm:<name>.

7Initialize a WorksGood project

cd /path/to/your/project
wg init

Creates .wg/ (task graph as JSONL, config, agency, service state). A fresh project is graph-only — no LLM route, no credentials. You can open the TUI now, but dispatching LLM work needs step 8.

Existing users: the commands below select a route; they do not delete profiles you already configured. Project-scoped selection (wg profile select) leaves your global ~/.wg/config.toml untouched.

8Select the Pi route with your free model

For a zero-cost smoke test, set both the strong (worker) and weak (agency one-shots) tiers to the free model. Path A — project-scoped (recommended; does not change global state):

wg profile init-starters
wg profile pi --strong "pi:openrouter/nvidia/nemotron-3-ultra-550b-a55b:free" \
              --weak   "pi:openrouter/nvidia/nemotron-3-ultra-550b-a55b:free"
wg profile select pi      # this project only; global config untouched

Path B — global (make Pi your default everywhere): same first two lines, then wg profile use pi (rewrites ~/.wg/config.toml, ensures the plugin, hot-reloads the daemon).

Path C — one explicit route:

wg setup --route pi --yes --model "pi:openrouter/nvidia/nemotron-3-ultra-550b-a55b:free"

Note: Path C sets worker tiers to your model but leaves the weak/agency tier on paid deepseek/deepseek-chat. Use A or B for a fully free test. Preview any path with --dry-run. Replace the id with whatever pi --list-models ":free" returns and you validated in step 4.

Verify the effective policy:

wg config --models

Every displayed LLM role must show handler pi, an exact pi:openrouter/<model>:free route, and a visible reasoning level. A missing/non-Pi route or omitted reasoning fails closed — no silent fallback.

Opening the TUI never selects a route. wg tui is graph-only and non-mutating: it will not initialize a graph, install packages, authenticate, pick a model, or start/reload the service. You must select Pi explicitly.

9Start the service and open the TUI

wg service start        # start the coordinator/dispatcher
wg service status       # health, daemon PID, dispatcher state
wg tui                  # the operating surface

Add a task, then explicitly release it for dispatch:

wg add "Smoke test: print hello from a free model" --exec-mode shell
wg publish <task-id> --only

Restart after config/package changes:

wg service reload       # pick up config.toml edits
wg service stop && wg service start   # full restart

Troubleshooting

wg: command not found / pi: command not found

~/.cargo/bin (wg) or your npm global bin (pi) isn't on PATH:

echo 'export PATH="$HOME/.cargo/bin:$(npm config get prefix)/bin:$PATH"' >> ~/.bashrc
source ~/.bashrc

Confirm the right binary wins — WorksGood's wg can be shadowed by WireGuard's wg(8). Check command -v wg.

Failed to run wg: No such file or directory (os error 2) (from the TUI)

A long-running installed wg tui couldn't re-exec itself after the binary was replaced (e.g. a cargo install while the TUI was open). WorksGood now self-execs via /proc/self/exe on Linux — restart the TUI from the installed binary after reinstalling:

wg service stop 2>/dev/null; pkill -f 'wg tui' 2>/dev/null
cargo install --git https://github.com/graphwork/wg
wg tui

role=default has no explicit Pi route / WG-PI-ROUTE-MISSING

You queried a project before selecting Pi. Run step 8, then wg config --models.

compatible plugin build missing / pi-worksgood not loaded

wg pi-plugin install, then wg pi-plugin status (expect console wired: yes).

Pi compat mismatch (extension=X wg=Y)

wg pi-plugin install re-materializes the build matching this wg.

401 / unauthorized from the model

Pi's OpenRouter auth is missing or stale. In a pi session: /login openrouter (or /logout then /login). WorksGood does not handle provider credentials — all auth lives in Pi's ~/.pi/agent/auth.json.

404 / model not available

The free id is wrong/withdrawn. Re-run pi --list-models ":free", re-validate with pi --model ... -p "...", then update your route.

Config changes not taking effect

wg service reload            # or stop+start for a full restart
wg config lint              # read-only check for stale keys
wg migrate config --dry-run # preview legacy-key rewrites

Concierge and expert boundary

The installed worksgood concierge provides the attended lifecycle path. The explicit commands above remain the auditable expert path under wg. worksgood is not a CLI rename and intentionally does not expose task/tool verbs; there is no worksg alias. Bare wg and wg tui remain non-mutating, and pi-worksgood continues to invoke wg for its complete backend contract.
